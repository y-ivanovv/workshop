```powershell
Invoke-RestMethod -Uri http://127.0.0.1:8080/actuator/health | ConvertTo-Json
```

Ожидаемый ответ:

```json

  "status": "UP"
```

## Данные и контракты второго этапа

`AppealCategory` — это `enum`, то есть закрытый список категорий:

| Значение | Назначение |
| --- | --- |
| `CREDITS` | Кредиты |
| `CARDS` | Банковские карты |
| `TRANSFERS` | Переводы |
| `OTHER` | Недостаточно данных для однозначного выбора |

`OTHER` — допустимый результат классификации, а не ошибка провайдера.

DTO (Data Transfer Object) описывает данные, которыми приложение обменивается через HTTP. Здесь это небольшие Java `record`: Java сама создаёт конструктор и методы чтения полей, поэтому ручные getters и setters не нужны. Например, у `ClassifyAppealRequest` текст читается методом `text()`.

- `ClassifyAppealRequest(String text)` — входное обращение. `@NotBlank` запрещает `null`, пустую строку и строку из пробелов. `@Size(max = 2000)` ограничивает длину исходной строки, до удаления пробелов по краям. В JSON поле должно быть строкой: `JsonConfiguration` запрещает автоматическое преобразование чисел и boolean в текст.
- `ClassifyAppealResponse(AppealCategory category)` — ответ с единственным полем категории.
- `ApiError(String code, String message)` — общий формат сообщения об ошибке.

JSON-запрос к `POST /api/appeals/classify`:

```json
{"text":"Как погасить кредит?"}
```

Ответ HTTP 200:

```json
{"category":"CREDITS"}
```

Аннотации описывают ограничения, но конструктор `record` не запускает их проверку самостоятельно. В контроллере проверку включает `@Valid`. Она выполняется до вызова сервиса, поэтому ограничение длины применяется до удаления пробелов по краям.

`LlmClient` — интерфейс: он задаёт общий набор методов для провайдеров, а сам алгоритм находится в реализациях:

```java
String providerName();
LlmResponse generate(LlmRequest request);
```

`providerName()` возвращает имя для выбора по настройкам. `generate(...)` принимает `LlmRequest` и возвращает `LlmResponse`. Две реализации описаны ниже.

`LlmRequest(String instruction, String text)` передаёт постоянную инструкцию приложения отдельно от текста клиента. `LlmResponse(AppealCategory category)` возвращает типизированную категорию. Эти внутренние модели отделены от публичных DTO: изменение конкретного провайдера не должно менять HTTP API. Gateway проверяет, что ответ и категория не равны `null`.

## Эмуляции и Gateway третьего этапа

`OpenAiLlmClient` носит имя из задания, но **не обращается к OpenAI**. Он ищет целые слова из небольших наборов:

- Кредиты: `кредит`, `кредита`, `кредиту`, `кредитом`, `кредите`, `кредиты`, `кредитов`, `кредитам`, `кредитами`, `кредитах`, `ипотека`, `ипотеки`, `ипотеку`, `ипотекой`, `ипотеке`.
- Карты: `карта`, `карты`, `карте`, `карту`, `картой`, `карт`, `картам`, `картами`, `картах`, `карточка`, `карточки`, `карточке`, `карточку`, `карточкой`.
- Переводы: `перевод`, `перевода`, `переводу`, `переводом`, `переводе`, `переводы`, `переводов`, `переводам`, `переводами`, `переводах`, `перевести`.

`InternalLlmClient` — независимая заглушка. Она знает только три точных слова: `кредит`, `карта`, `перевод`.

Обе реализации приводят текст к нижнему регистру и разбивают его на слова по пробелам и знакам препинания. Буквы, цифры и знак подчёркивания остаются частью слова: `картина`, `карта_тест` и `кредит123` не совпадают с ключевыми словами. Если найдена ровно одна группа, возвращается её категория. Если не найдена ни одна или найдены несколько групп — `OTHER`. Считаются только слова, которые знает конкретная эмуляция.

| Обращение | `openai` | `internal` |
| --- | --- | --- |
| Хочу оформить кредит | `CREDITS` | `CREDITS` |
| Нужна карта | `CARDS` | `CARDS` |
| Где мой перевод? | `TRANSFERS` | `TRANSFERS` |
| Нужна ипотека | `CREDITS` | `OTHER` |
| Не могу оплатить картой | `CARDS` | `OTHER` |
| Карта и перевод | `OTHER` | `OTHER` |
| Мне нужна картина и переводчик | `OTHER` | `OTHER` |

Это алгоритмы по ключевым словам, а не настоящие языковые модели. Они не понимают отрицания и смысл текста: например, «Мне не нужна карта» всё равно даст `CARDS`. Сложные обращения, неизвестные слова и сочетания распознанных и нераспознанных тем могут классифицироваться неверно. Инструкция из `LlmRequest` не исполняется; эмуляции анализируют только поле `text`.

`@Component` позволяет Spring создать объекты обеих реализаций. Конструктор `AiGateway` получает список `LlmClient` и выбирает нужный объект по имени. Вызывающему коду достаточно вызвать `gateway.generate(request)` — ему не нужно создавать конкретный провайдер.

Настройки в `application.yml`:

```yaml
llm:
  active-provider: openai
  fallback-provider: internal
  timeout: 1s
  max-attempts: 2
```

`LlmProperties` — `record` с этими четырьмя значениями. `@EnableConfigurationProperties` в точке входа регистрирует его в Spring, а `@ConfigurationProperties(prefix = "llm")` указывает раздел YAML. Spring сопоставляет `active-provider` с полем `activeProvider` и преобразует `1s` в `Duration`.

При запуске проверяются непустые имена, положительное время и число попыток от 1 до 3. Gateway проверяет, что оба имени зарегистрированы, они различаются и у реализаций нет повторяющихся имён. Неправильные настройки прерывают запуск с сообщением об ошибке.

Этап 3 подготовил маршрутизацию и настройки. Начиная с этапа 5 все четыре настройки участвуют в выполнении запросов; правила обработки сбоев описаны ниже.

Чтобы сменить основной провайдер, поменяйте обе строки местами по значениям:

```yaml
llm:
  active-provider: internal
  fallback-provider: openai
  timeout: 1s
  max-attempts: 2
```

После изменения YAML перезапустите приложение через `mvn spring-boot:run`; для запуска JAR сначала пересоберите его. Проверить оба варианта маршрутизации можно командой `mvn test`: тест конфигурации отправляет «Нужна ипотека» и проверяет разные ответы. То же обращение теперь можно отправить через HTTP, как показано ниже.

Тесты конфигурации используют небольшой Spring-контекст с `ApplicationContextRunner`, без HTTP-сервера и без `@SpringBootTest`.

## REST API и слои четвёртого этапа

Путь запроса:

```text
HTTP JSON → AppealController → AppealClassificationService
          → ClassificationClient → AiGateway → выбранный LlmClient
```

`AppealController` принимает JSON, включает проверку DTO через `@Valid` и возвращает DTO с категорией. Контроллер знает только сервис и не выбирает провайдера.

`AppealClassificationService` получает текст, убирает пробелы по краям через `strip()` и передаёт его в `ClassificationClient`. Сервис возвращает доменную категорию, не зависит от HTTP и не знает имён LLM-провайдеров.

`ClassificationClient` создаёт `LlmRequest`: постоянная инструкция перечисляет категории и правила, а текст клиента хранится отдельно. Результат Gateway преобразуется в доменную категорию. Внутренние модели LLM остаются внутри клиентского слоя.

Чтобы отправить обращение, запустите приложение и во втором окне PowerShell выполните:

```powershell
$body = @{ text = "Как погасить кредит?" } | ConvertTo-Json
Invoke-RestMethod -Method Post `
    -Uri http://127.0.0.1:8080/api/appeals/classify `
    -ContentType "application/json; charset=utf-8" `
    -Body ([System.Text.Encoding]::UTF8.GetBytes($body)) | ConvertTo-Json
```

Ожидаемый ответ:

```json
{"category":"CREDITS"}
```

Байты UTF-8 указаны явно, чтобы русский текст передавался одинаково из разных версий PowerShell. Замените текст на «Нужна ипотека», чтобы сравнить `openai` и `internal` после смены настроек и перезапуска. Непонятное или неоднозначное обращение возвращает HTTP 200 с `OTHER`.

### Ошибки API

`ApiExceptionHandler` помечен `@RestControllerAdvice`: это общий обработчик ошибок HTTP-слоя. Он возвращает `ApiError` и сохраняет нужный HTTP-статус. Базовый класс `ResponseEntityExceptionHandler` помогает обрабатывать стандартные ошибки Spring и сохранять служебные заголовки, например `Allow: POST` при ошибке 405.

| HTTP | `code` | Когда возникает |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | Неверный JSON, отсутствие текста, пустой или слишком длинный текст |
| 404 | `NOT_FOUND` | Неизвестный адрес |
| 405 | `METHOD_NOT_ALLOWED` | Например, GET вместо POST для классификации |
| 406 | `NOT_ACCEPTABLE` | Клиент требует ответ в неподдерживаемом формате, например XML |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Тело отправлено не как JSON |
| 503 | `CLASSIFICATION_UNAVAILABLE` | Сигнал о недоступности классификации |
| 500 | `INTERNAL_ERROR` | Неожиданная ошибка приложения |

Пример ответа на пустой текст:

```json
{
  "code": "INVALID_REQUEST",
  "message": "Текст обращения должен содержать от 1 до 2000 символов"
}
```

Обработчик не возвращает клиенту исходные сообщения исключений, stack trace и текст обращения. Ошибки явно отправляются как JSON, в том числе сообщение о неподдерживаемом формате ответа. Сервис не подменяет сбой результатом `OTHER`: исключение проходит до обработчика ошибок.

Gateway выбрасывает `ClassificationUnavailableException`, если основной и резервный провайдеры не смогли дать корректный ответ. Обработчик превращает это исключение в 503. Неожиданная ошибка программирования не маскируется fallback и приводит к безопасному 500.

HTTP-тесты используют `@WebMvcTest` и `MockMvc`: Spring проверяет маршруты, JSON, валидацию и обработчик без открытия сетевого порта. Сервис заменён через `@MockitoBean`; отдельно есть unit-тесты сервиса с mock клиентом и клиента с mock Gateway. Это позволяет проверить ответственность каждого слоя.

## Устойчивость и наблюдаемость пятого этапа

### Таймаут, повторы и fallback

`timeout: 1s` означает: ждать результат одной попытки не дольше одной секунды. `max-attempts: 2` означает первый вызов основного провайдера и не более одного повтора. После исчерпания попыток резерв вызывается один раз с тем же таймаутом. При свободном исполнителе ожидание провайдеров с этими настройками занимает примерно до трёх секунд плюс небольшие накладные расходы.

| Результат основного провайдера | Действие Gateway |
| --- | --- |
| Корректная категория, включая `OTHER` | Сразу вернуть результат |
| `TemporaryLlmException` или таймаут | Повторить, если остались попытки; иначе перейти к резерву |
| `PermanentLlmException` | Сразу перейти к резерву |
| `null`, пустая категория или `InvalidLlmResponseException` | Сразу перейти к резерву |
| Заполненная очередь | Без повторов попробовать резерв один раз; при отказе вернуть 503 |
| Прерывание обработки | Отменить ожидание, прекратить работу без повторов и fallback |
| Неожиданная ошибка программирования | Передать ошибку в HTTP-слой для безопасного ответа 500 |

Резерв не вызывает основной провайдер обратно и сам не повторяется. Его ожидаемый сбой, таймаут или неправильный ответ завершаются 503. `OTHER` означает допустимый неопределённый результат, поэтому не включает fallback.

Чтобы реально ограничить ожидание, вызов провайдера выполняется в `ThreadPoolExecutor`. Это два рабочих потока внутри приложения и очередь на десять задач, а не отдельный сервис. `Future` представляет результат запущенной задачи; `Future.get(...)` ждёт его с таймаутом. Ожидание в очереди тоже входит в лимит попытки.

После таймаута вызывается `cancel(true)`: задача получает запрос на прерывание. Отменённая задача удаляется из очереди, чтобы освободить место. При остановке Spring вызывает `shutdownNow()` у исполнителя. Если прерван ожидающий поток, Gateway восстанавливает его флаг прерывания и прекращает обработку. Эмуляции проверяют прерывание во время обработки слов.

Отмена кооперативная: Java не может принудительно остановить произвольный код, который игнорирует прерывание. Для будущего настоящего HTTP-провайдера дополнительно потребуются сетевые таймауты клиента. Сейчас провайдеры локальные и не имитируют случайные сбои: медленные ответы и ошибки задаются только в тестах. Публичного переключателя сбоев нет.

### Безопасные логи

Пример записи:

```text
LLM provider=openai attempt=1 outcome=success duration_ms=2
```

Gateway записывает только имя провайдера, номер попытки, исход, длительность и переход к резерву. Текст обращения, инструкция, категория ответа, API-ключи, сообщения и stack trace исключений в эти записи не попадают.

### Метрики LLM

| Метрика | Что измеряет |
| --- | --- |
| `llm.calls` | Число попыток, включая таймауты и отказы исполнителя принять задачу |
| `llm.call.duration` | Количество и длительность попыток, включая ожидание в очереди |
| `llm.fallbacks` | Число переходов к резервному провайдеру |

У первых двух метрик есть только теги `provider` и `outcome`. Допустимые исходы: `success`, `timeout`, `temporary_error`, `permanent_error`, `invalid_response`, `rejected`, `interrupted`, `unexpected_error`. Два последних отдельно обозначают прерывание и неожиданную ошибку, чтобы не считать их постоянными сбоями провайдера. Счётчик fallback не имеет тегов.

После отправки хотя бы одного обращения метрики можно посмотреть из PowerShell:

```powershell
Invoke-RestMethod -Uri http://127.0.0.1:8080/actuator/metrics/llm.calls | ConvertTo-Json -Depth 5
Invoke-RestMethod -Uri http://127.0.0.1:8080/actuator/metrics/llm.call.duration | ConvertTo-Json -Depth 5
Invoke-RestMethod -Uri http://127.0.0.1:8080/actuator/metrics/llm.fallbacks | ConvertTo-Json -Depth 5
```

Отфильтровать успешные попытки основного провайдера:

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8080/actuator/metrics/llm.calls?tag=provider:openai&tag=outcome:success" | ConvertTo-Json -Depth 5
```

В `measurements` счётчика смотрите `COUNT`; у таймера доступны `COUNT`, `TOTAL_TIME` и `MAX`. За один HTTP-запрос может быть несколько попыток, поэтому счётчик LLM не равен числу HTTP-запросов. При обычных успешных вызовах локальной эмуляции `llm.fallbacks` остаётся равным нулю. Невалидный HTTP-вход вообще не доходит до Gateway и не создаёт попытку.

Проверки сбоев запускаются командой `mvn test`. В тестах задержки управляются `CountDownLatch`, чтобы проверять реальный таймаут и отмену без случайных `sleep`. Проверяются повтор после таймаута и временной ошибки, переход к резерву, отказ обоих провайдеров, неправильный ответ, переполнение очереди, прерывание, завершение исполнителя и отсутствие содержимого запроса в логах и метриках.

## Проверка важных сценариев на шестом этапе

Покрытие сверено с разделом 10 SPEC по поведению системы. Процент строк или ветвей не вычисляется. Новые проверки нужны для конкретных рисков, а не для увеличения числа тестов.

| Что проверяется | Где |
| --- | --- |
| Обязательность текста, длины 1/2000/2001, чтение и формат JSON | `ClassifyAppealRequestTest`, `ApiJsonContractTest` |
| Категории, регистр, словоформы, неоднозначность и ложные совпадения | `LlmEmulationTest` |
| Удаление пробелов и передача ошибки недоступности | `AppealClassificationServiceTest` с mock клиентом |
| Разделение инструкции и текста, возврат категории | `ClassificationClientTest` с mock Gateway |
| Смена провайдера, ошибки настроек и закрытие исполнителя | `LlmConfigurationTest` |
| Повторы с лимитами 1/2/3, разные сбои резерва, некорректный ответ и неожиданные ошибки | `AiGatewayTest` |
| Таймаут, отмена, очередь, прерывание, логи и метрики | `AiGatewayTest`, `LlmEmulationTest` |
| Успех, ошибки входа и типов JSON, 404/405/406/415/500/503 | `AppealControllerTest` с `@WebMvcTest` |

Проверка выявила и исправила два пропуска: числа и boolean раньше автоматически становились строками, а ответ 406 при `Accept: application/xml` мог остаться без JSON-тела. Теперь оба случая закреплены тестами. Новых зависимостей и измерительных плагинов не добавлено.

Все тесты лежат в `src/test/java/ru/ivanov/workshop/`. Запуск: `mvn test`; итоговая сборка с теми же тестами: `mvn clean package`. Фактический результат текущего этапа записан в разделе 14 SPEC. Детальные отчёты последнего запуска находятся в `target/surefire-reports/` и не отправляются в Git.

`README-AI.md` фиксирует границы слоёв, контракт API, безопасность, правила Gateway и требования к тестам. Он будет частью контекста для эксперимента следующего этапа. Сам эксперимент с двумя ответами AI, разбор прототипа и отчёт ещё не выполнены.
