## Текущее состояние

Завершены этапы 1–3: создана основа приложения, добавлены категории обращений, DTO, две локальные эмуляции `LlmClient`, настройки и базовый `AiGateway`. Gateway выбирает провайдера по конфигурации. Приложение предоставляет проверку состояния и базовые метрики.

Классификация через Java-интерфейс уже проверяется тестами. HTTP endpoint `POST /api/appeals/classify` появится на этапе 4. На главной странице `/` сейчас возвращается HTTP 404: страницы сайта в проекте нет.

## Требования

- JDK 21.
- Maven 3.6.3 или новее.
- Доступ в интернет при первой сборке для загрузки библиотек.

Версия Spring Boot — **3.5.16**, версия проекта — **0.0.1-SNAPSHOT**. Обе зафиксированы в `pom.xml`. Spring Boot управляет совместимыми версиями библиотек, поэтому каждую из них отдельно не настраиваем.

Проверить установленные Java и Maven:

```powershell
java -version
mvn -version
```

Команды ниже выполняются из папки с `pom.xml`.

## Сборка и запуск

Собрать приложение:

```powershell
mvn clean package
```

Maven скомпилирует Java-код, выполнит тесты и создаст запускаемый архив `target/workshop-0.0.1-SNAPSHOT.jar`. Тесты проверяют ограничения текста, JSON, правила эмуляций, маршрутизацию и конфигурацию.

Запустить приложение:

```powershell
mvn spring-boot:run
```

Оставьте это окно терминала открытым. Во втором окне PowerShell выполните:

```powershell
Invoke-RestMethod -Uri http://127.0.0.1:8080/actuator/health | ConvertTo-Json
```

Ожидаемый ответ:

```json
{
  "status": "UP"
}
```

`UP` означает, что приложение запущено и его проверка состояния проходит.

Посмотреть список базовых метрик:

```powershell
Invoke-RestMethod -Uri http://127.0.0.1:8080/actuator/metrics | ConvertTo-Json
```

Метрики вызовов LLM будут добавлены на этапе 5. Пока доступны стандартные метрики приложения и Java.

Остановить приложение можно сочетанием **Ctrl+C** в окне запуска. Если порт 8080 занят, для разового запуска на другом порту используйте:

```powershell
mvn spring-boot:run "-Dspring-boot.run.arguments=--server.port=8081"
```

В адресах проверочных запросов тогда тоже замените 8080 на 8081.

Собранный архив также можно запустить без Maven:

```powershell
java -jar target/workshop-0.0.1-SNAPSHOT.jar
```

Это второй способ запуска того же приложения. Чтобы выполнить только тесты, используйте `mvn test`.

## Как устроена основа

```text
pom.xml                                      — зависимости и настройки сборки
src/main/java/ru/ivanov/workshop/
    WorkshopApplication.java                 — точка запуска
    domain/AppealCategory.java                — допустимые категории
    dto/                                     — данные HTTP-запросов и ответов
    llm/                                     — контракт, две эмуляции и Gateway
    config/LlmProperties.java                 — чтение и проверка настроек LLM
src/main/resources/application.yml           — настройки приложения
src/test/java/ru/ivanov/workshop/              — проверки DTO, эмуляций и настроек
.gitignore                                   — файлы, которые не нужно сохранять в Git
SPEC.md                                      — план этапов и архитектурные решения
```

В `WorkshopApplication` находится метод `main`, с которого начинается выполнение Java-программы. `SpringApplication.run(...)` запускает Spring Boot. Аннотация `@SpringBootApplication` включает настройку приложения и поиск его компонентов в пакете `ru.ivanov.workshop` и вложенных пакетах.

В `pom.xml` подключены только зависимости, предусмотренные SPEC:

| Зависимость | Для чего нужна |
| --- | --- |
| Spring Web | HTTP-сервер и будущий REST API |
| Validation | Проверка входных данных на следующих этапах |
| Actuator | Проверка состояния и метрики |
| Spring Boot Test | JUnit и Mockito для тестов; не входит в рабочий архив |

В `application.yml` заданы имя приложения, локальный адрес `127.0.0.1`, порт 8080 и два доступных диагностических endpoint: health и metrics.

База данных, Docker и API-ключи для запуска не нужны. Оба LLM-провайдера — локальные эмуляции без сетевых запросов. Реальный банковский сервис в рамках работы не создаётся.

## Данные и контракты второго этапа

`AppealCategory` — это `enum`, то есть закрытый список категорий:

| Значение | Назначение |
| --- | --- |
| `CREDITS` | Кредиты |
| `CARDS` | Банковские карты |
| `TRANSFERS` | Переводы |
| `OTHER` | Недостаточно данных для однозначного выбора |

`OTHER` — допустимый результат классификации, а не ошибка провайдера.

DTO (Data Transfer Object) описывает данные, которыми приложение обменивается через HTTP. Здесь это небольшие Java `record`: Java сама создаёт конструктор и методы чтения полей, поэтому ручные getters и setters не нужны. Например, у `ClassifyAppealRequest` текст читается методом `text()`.

- `ClassifyAppealRequest(String text)` — входное обращение. `@NotBlank` запрещает `null`, пустую строку и строку из пробелов. `@Size(max = 2000)` ограничивает длину исходной строки, до удаления пробелов по краям.
- `ClassifyAppealResponse(AppealCategory category)` — ответ с единственным полем категории.
- `ApiError(String code, String message)` — общий формат сообщения об ошибке.

Подготовленный JSON-контракт будущего endpoint `POST /api/appeals/classify`:

```json
{"text":"Как погасить кредит?"}
```

Пример будущего ответа:

```json
{"category":"CREDITS"}
```

Сам endpoint появится на этапе 4. Аннотации описывают ограничения, но конструктор `record` не запускает их проверку самостоятельно. Сейчас правила проверяются валидатором в тестах; в контроллере на этапе 4 включим их через `@Valid`.

`LlmClient` — интерфейс: он задаёт общий набор методов для провайдеров, а сам алгоритм находится в реализациях:

```java
String providerName();
LlmResponse generate(LlmRequest request);
```

`providerName()` возвращает имя для выбора по настройкам. `generate(...)` принимает `LlmRequest` и возвращает `LlmResponse`. Две реализации описаны ниже.

`LlmRequest(String instruction, String text)` передаёт постоянную инструкцию приложения отдельно от текста клиента. `LlmResponse(AppealCategory category)` возвращает типизированную категорию. Эти внутренние модели отделены от публичных DTO: изменение конкретного провайдера не должно менять HTTP API. Проверку ответа провайдера, включая `null`, позже выполняет Gateway.

## Эмуляции и Gateway третьего этапа

`OpenAiLlmClient` носит имя из задания, но **не обращается к OpenAI**. Он ищет целые слова из небольших наборов:

- Кредиты: `кредит`, `кредита`, `кредиту`, `кредитом`, `кредите`, `кредиты`, `кредитов`, `кредитам`, `кредитами`, `кредитах`, `ипотека`, `ипотеки`, `ипотеку`, `ипотекой`, `ипотеке`.
- Карты: `карта`, `карты`, `карте`, `карту`, `картой`, `карт`, `картам`, `картами`, `картах`, `карточка`, `карточки`, `карточке`, `карточку`, `карточкой`.
- Переводы: `перевод`, `перевода`, `переводу`, `переводом`, `переводе`, `переводы`, `переводов`, `переводам`, `переводами`, `переводах`, `перевести`.

`InternalLlmClient` — независимая заглушка. Она знает только три точных слова: `кредит`, `карта`, `перевод`.

Обе реализации приводят текст к нижнему регистру и разбивают его на слова по пробелам и знакам препинания. Буквы, цифры и знак подчёркивания остаются частью слова: `картина`, `карта_тест` и `кредит123` не совпадают с ключевыми словами. Если найдена ровно одна группа, возвращается её категория. Если не найдена ни одна или найдены несколько групп — `OTHER`. Считаются только слова, которые знает конкретная эмуляция.

| Обращение | `openai` | `internal` |
| --- | --- | --- |
| Хочу оформить кредит | `CREDITS` | `CREDITS` |
| Нужна карта | `CARDS` | `CARDS` |
| Где мой перевод? | `TRANSFERS` | `TRANSFERS` |
| Нужна ипотека | `CREDITS` | `OTHER` |
| Не могу оплатить картой | `CARDS` | `OTHER` |
| Карта и перевод | `OTHER` | `OTHER` |
| Мне нужна картина и переводчик | `OTHER` | `OTHER` |

Это алгоритмы по ключевым словам, а не настоящие языковые модели. Они не понимают отрицания и смысл текста: например, «Мне не нужна карта» всё равно даст `CARDS`. Сложные обращения, неизвестные слова и сочетания распознанных и нераспознанных тем могут классифицироваться неверно. Инструкция из `LlmRequest` не исполняется; эмуляции анализируют только поле `text`.

`@Component` позволяет Spring создать объекты обеих реализаций. Конструктор `AiGateway` получает список `LlmClient` и выбирает нужный объект по имени. Вызывающему коду достаточно вызвать `gateway.generate(request)` — ему не нужно создавать конкретный провайдер.

Настройки в `application.yml`:

```yaml
llm:
  active-provider: openai
  fallback-provider: internal
  timeout: 1s
  max-attempts: 2
```

`LlmProperties` — `record` с этими четырьмя значениями. `@EnableConfigurationProperties` в точке входа регистрирует его в Spring, а `@ConfigurationProperties(prefix = "llm")` указывает раздел YAML. Spring сопоставляет `active-provider` с полем `activeProvider` и преобразует `1s` в `Duration`.

При запуске проверяются непустые имена, положительное время и число попыток от 1 до 3. Gateway проверяет, что оба имени зарегистрированы, они различаются и у реализаций нет повторяющихся имён. Неправильные настройки прерывают запуск с сообщением об ошибке.

На этапе 3 Gateway только вызывает активный провайдер. Резервный провайдер, таймаут и число попыток пока читаются и проверяются; автоматическое переключение, ограничение времени, повторы, проверка ответа и метрики LLM появятся на этапе 5. Наличие этих полей в YAML пока не включает обработку сбоев.

Чтобы сменить основной провайдер, поменяйте обе строки местами по значениям:

```yaml
llm:
  active-provider: internal
  fallback-provider: openai
  timeout: 1s
  max-attempts: 2
```

После изменения YAML перезапустите приложение через `mvn spring-boot:run`; для запуска JAR сначала пересоберите его. Проверить оба варианта маршрутизации сейчас можно командой `mvn test`: тест конфигурации отправляет «Нужна ипотека» и проверяет разные ответы. После этапа 4 это можно будет повторить через HTTP.

Тесты конфигурации используют небольшой Spring-контекст с `ApplicationContextRunner`, без HTTP-сервера и без `@SpringBootTest`.
