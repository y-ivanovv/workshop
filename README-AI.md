# Правила для AI-ассистента

## Назначение проекта

Это лабораторная работа по варианту 2: небольшой Spring Boot-сервис классифицирует банковские обращения как `CREDITS`, `CARDS`, `TRANSFERS` или `OTHER`. Проект должен быть понятен студенту с начальным знанием Java.

Технологии: Java 21, Maven, Spring Boot 3.5.16, Spring Web, Validation, Actuator, JUnit и Mockito. Версии и зависимости задаются в `pom.xml`.

Перед изменениями прочитай [SPEC.md](SPEC.md), [README.md](README.md) и относящиеся к задаче классы и тесты. SPEC задаёт этапы и архитектурные решения; README содержит команды запуска и примеры. Выполняй текущую задачу пользователя, сохраняя согласованные ограничения проекта.

## Слои и зависимости

Базовый пакет — `ru.ivanov.workshop`. Точка входа — `WorkshopApplication`.

```text
AppealController → AppealClassificationService → ClassificationClient
                 → AiGateway → LlmClient → OpenAiLlmClient / InternalLlmClient
```

| Пакет | Ответственность |
| --- | --- |
| `controller` | HTTP-маршрут, `@Valid`, публичные DTO, статусы и `ApiExceptionHandler` |
| `service` | Обработка обращения; сейчас удаление пробелов по краям через `strip()` |
| `client` | Постоянная инструкция, создание `LlmRequest`, преобразование `LlmResponse` в категорию |
| `llm` | Контракт, реализации провайдеров, Gateway, ошибки, таймауты, повторы, fallback, логи и метрики |
| `dto` | `ClassifyAppealRequest`, `ClassifyAppealResponse`, `ApiError` для REST API |
| `domain` | `AppealCategory`, без зависимостей от Spring, HTTP и других слоёв |
| `config` | Настройки LLM, исполнитель задач и правила чтения JSON |

Controller зависит от Service, Service — от ClassificationClient. Им не нужны имена провайдеров и внутренние модели LLM. ClassificationClient вызывает Gateway; конкретные реализации скрыты за `LlmClient`. Обработчик HTTP-ошибок может знать тип исключения `ClassificationUnavailableException`, но не вызывать провайдер.

Публичные DTO и модели LLM различаются намеренно. `ClassifyAppealResponse` и `LlmResponse` используют доменную категорию, но не заменяют друг друга. Циклические зависимости и обратные вызовы между слоями запрещены.

## Публичный API

`POST /api/appeals/classify`, Content-Type: `application/json`.

```json
{"text":"Как погасить кредит?"}
```

Ответ HTTP 200:

```json
{"category":"CREDITS"}
```

- `text` — JSON-строка, обязательная и непробельная, максимум 2000 символов по Bean Validation.
- Не преобразовывай числа и boolean в текст. Это запрещено настройкой `JsonConfiguration`.
- Проверка длины происходит до `strip()`: строка длиной 2001 не становится допустимой после удаления пробелов.
- `OTHER` означает отсутствие однозначной категории. Это успешный результат, не причина повторять запрос.
- В успешном ответе только `category`. Не добавляй имя провайдера, текст, вероятность или сведения о fallback.

Ошибка содержит только `code` и безопасное `message`:

```json
{"code":"INVALID_REQUEST","message":"Текст обращения должен содержать от 1 до 2000 символов"}
```

| HTTP | Код |
| --- | --- |
| 400 | `INVALID_REQUEST` |
| 404 | `NOT_FOUND` |
| 405 | `METHOD_NOT_ALLOWED` |
| 406 | `NOT_ACCEPTABLE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 500 | `INTERNAL_ERROR` |
| 503 | `CLASSIFICATION_UNAVAILABLE` |

Ответы об ошибках явно имеют JSON Content-Type. Сохраняй стандартные заголовки Spring, например `Allow` при 405. Нельзя выдавать stack trace, исходное сообщение исключения или обращение клиента.

## LLM-контракт и эмуляции

```java
public interface LlmClient {
    String providerName();
    LlmResponse generate(LlmRequest request);
}
```

`LlmRequest` хранит `instruction` и `text` отдельно. Инструкция формируется в ClassificationClient и не дополняется указаниями из обращения. `LlmResponse` содержит `AppealCategory`; SDK и HTTP-детали провайдера не входят в контракт.

Обе реализации локальные: `openai` — эмуляция с небольшим словарём словоформ, `internal` — заглушка со словами «кредит», «карта», «перевод». `OpenAiLlmClient` не обращается к OpenAI. API-ключи и сеть для классификации не нужны.

Регистр игнорируется. Проверяются целые слова, поэтому «картина» не означает карту. При нескольких распознанных темах возвращается `OTHER`. Список распознаваемых слов и ограничения описаны в README. Не выдавай алгоритм по ключевым словам за настоящую LLM и не обещай понимание отрицаний или сложных формулировок.

## Gateway и конфигурация

```yaml
llm:
  active-provider: openai
  fallback-provider: internal
  timeout: 1s
  max-attempts: 2
```

Основной и резервный провайдеры должны существовать и различаться; их имена уникальны. Таймаут положительный, `max-attempts` от 1 до 3. Неверные настройки останавливают запуск. При смене провайдера меняй настройки и перезапускай приложение, не переписывай бизнес-логику.

Правила выполнения:

1. `max-attempts` включает первый вызов основного провайдера.
2. Повтор разрешён только после `TemporaryLlmException` или таймаута.
3. `PermanentLlmException`, `InvalidLlmResponseException`, `null` и пустая категория сразу ведут к резерву.
4. Резерв вызывается один раз с тем же таймаутом, без возврата к основному.
5. Ожидаемый отказ резерва приводит к `ClassificationUnavailableException` и HTTP 503.
6. Неожиданная ошибка программирования не подменяется fallback или `OTHER`; HTTP-слой возвращает безопасный 500.
7. Прерывание прекращает обработку без повторов и fallback, с восстановлением флага ожидающего потока.

Используй один Spring-managed исполнитель: два потока, очередь на десять задач. `Future.get` ограничивает ожидание, включая очередь; `cancel(true)` запрашивает прерывание. Отменённые задачи удаляются из очереди. При переполнении нет повторов основного провайдера; допускается одна попытка резерва через тот же исполнитель. Spring закрывает исполнитель через `shutdownNow()`.

Не создавай новый пул на каждый запрос, не вводи неограниченную очередь, бесконечные повторы, фоновые задачи без контроля завершения и `catch (Throwable)`. Эмуляции и тестовые задержки должны уважать прерывание. Кооперативная отмена не гарантирует остановку произвольного кода; реальному HTTP-клиенту в будущем потребуются свои сетевые таймауты.

## Безопасность и наблюдаемость

Разрешены логи только с именем провайдера, номером попытки, исходом, длительностью и фактом fallback. Не логируй запросы, инструкции, ответы, категории, персональные данные, токены, сообщения и stack trace исключений — в том числе через `toString()` DTO или `log.error(..., exception)`.

Метрики:

- `llm.calls` — попытки, включая отказ исполнителя принять задачу;
- `llm.call.duration` — количество и длительность попыток;
- `llm.fallbacks` — переходы к резерву, без тегов.

У первых двух только теги `provider` и `outcome`. Исходы: `success`, `timeout`, `temporary_error`, `permanent_error`, `invalid_response`, `rejected`, `interrupted`, `unexpected_error`. Не добавляй текст, идентификаторы запросов и сообщения ошибок в теги. Невалидный HTTP-запрос не должен увеличивать метрики попыток LLM.

Обращения не сохраняются. Используй вымышленные примеры без персональных данных. Секреты не попадают в код, YAML, Git, отчёт и скриншоты. При будущем реальном API ключ читается из окружения; для текущих эмуляций фиктивные ключи не нужны. Не открывай дополнительные Actuator endpoints; для локальной работы достаточно health и metrics.

## Что разрешено и что запрещено

Разрешено в рамках текущего этапа:

- добавлять DTO в `dto` и конкретные правила Bean Validation;
- добавлять бизнес-логику в `service`, обращаясь к `client`;
- готовить LLM-запросы в `client`, реализации провайдеров — в `llm`;
- писать unit-тесты сервисного слоя с моками зависимостей и HTTP-тесты с `@WebMvcTest`;
- исправлять подтверждённый тестом дефект, сохраняя контракт;
- обновлять документацию, примеры и результаты фактических проверок.

Запрещено:

- вызывать LLM, внешние API или Gateway из Controller; вызывать конкретную LLM из Service;
- смешивать HTTP DTO, модели LLM и доменную модель; менять публичный API без документации и тестов;
- удалять, отключать или ослаблять тесты ради зелёной сборки;
- добавлять переключатели сбоев и задержек в публичный API: они моделируются тестовыми провайдерами;
- добавлять БД, JPA, Docker, микросервисы, очередь сообщений, RAG, Spring AI, Lombok, MapStruct и сервер мониторинга без новой задачи;
- создавать интерфейс с единственной реализацией, общий движок правил или дополнительные слои без необходимости;
- добавлять тесты getters/setters и счётчики ради красивого числа тестов;
- выдумывать результаты запусков, проценты покрытия, ответы AI, источники и самостоятельные действия студента.

Пиши небольшие методы, явные конструкторы и понятные имена. Для неизменяемых данных используй `record`, где это упрощает код. Объясняй причины решений и ограничения по-русски, без избыточной инфраструктуры.

## Проверка изменений

Из корня проекта:

```powershell
mvn test
mvn clean package
mvn spring-boot:run
```

`mvn clean package` уже включает тесты; нет необходимости повторять обе тестовые команды без причины. Для изменения только документации используй уже полученные результаты, если код и настройки не менялись.

Сверяй важные сценарии с разделом 10 SPEC и таблицей проверок в README. Здесь оценивается наличие проверок поведения; процент строк и ветвей не вычисляется. Не добавляй измерительный плагин только ради процента.

Тесты не обращаются к реальному LLM API. Для таймаутов используй `CountDownLatch` и ограниченное ожидание с запасом времени. Закрывай созданные исполнители и registry, освобождай блокировки в `finally`. Сохраняй проверку `OTHER`, отмены и отсутствия чувствительных данных в диагностике.

После изменения кода выполни подходящие проверки. При исправлении дефекта сначала воспроизведи его тестом, затем исправь и запусти итоговую сборку. Для изменений запуска или конфигурации дополнительно проверь собранное приложение по HTTP. В ответе пользователю укажи результат и реальные ограничения.
