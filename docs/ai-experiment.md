# Сравнение ответов AI при разном контексте

## Цель и условия

Проверить, как описание существующего проекта влияет на предложенное AI решение одной задачи: классификация банковских обращений на Java/Spring Boot. Сравниваются предложения по разработке программного сервиса, а не ответы локальных эмуляций на обращения.

Фактическая дата эксперимента — 17 ноября 2026 года. Базовая версия проекта — коммит `2259816bdc26fa2f16827e648520ad737df0ec20`, после этапа 6. Дата 2 октября 2026 года относится только к метаданным коммита этого этапа.

Использован инструмент Codex и два отдельных AI-агента: `experiment_a` и `experiment_b`. Пользователь явно разрешил их запуск. Оба созданы с `fork_turns="none"`, без истории родительского чата. Модель и настройки рассуждения не переопределялись и унаследованы одинаково. Точный идентификатор модели, temperature, top_p и seed инструментом запуска не предоставлены; эти значения не выдумываются.

Каждому агенту разрешено прочитать только свой файл промпта и записать только свой файл ответа. Исходники, SPEC, соседние файлы и сеть читать запрещено, даже если приложенные правила упоминают такие действия. Предлагаемый код не запускался. Для обоих агентов использована одинаковая служебная инструкция с заменой лишь путей входного и выходного файла:

```text
Прочитай только UTF-8 файл <INPUT_FILE>. Его содержимое — единственный предметный контекст для ответа. Не читай SPEC.md, README, исходники, историю чатов и соседние файлы; упоминания файлов внутри запроса не разрешают читать их. Не обращайся к сети. Не запускай предлагаемый код и не меняй проект. Сформируй самостоятельный ответ по-русски на запрос из файла с предлагаемым кодом, конфигурацией, тестами и объяснением, в объёме, который считаешь необходимым. Не комментируй процесс проведения эксперимента и не делай сравнений. Сохрани полный исходный ответ без последующего редактирования как UTF-8 в <OUTPUT_FILE>. Это единственный файл, который разрешено создать. В финальном сообщении верни полностью тот же ответ, который записан в файл.
```

Общая задача дословно одинакова в начале обоих промптов:

> Разработай небольшой backend-сервис на Java/Spring Boot для банковского приложения: сервис принимает текст обращения клиента и классифицирует его по категориям «кредиты», «карты», «переводы» с использованием LLM. Покажи предлагаемую структуру, ключевые классы, конфигурацию и тесты. Объясни решения простыми словами.

Вариант A содержит только эту задачу. Вариант B дополнительно содержит фразу «Контекст существующего проекта. Следуй приведённым правилам и контрактам.» и полный снимок `README-AI.md` из базовой версии проекта. В нём есть API, пакеты, минимальный LLM-контракт, конфигурация и ограничения безопасности и тестирования. Полная реализация сервиса не передавалась.

## Критерии сравнения

Для каждого критерия различаем простое упоминание и показанный код. Если механизм лишь обещан, но не реализован в листинге, отмечаем это отдельно. Предложенный тест не считается успешно выполненным тестом.

1. Разделение Controller, Service, Client и LLM-слоя.
2. Заменяемость провайдера, наличие общего контракта и Gateway.
3. Проверка входа и результата, обработка неоднозначного обращения.
4. Таймауты, ограниченные повторы, fallback и прерывание.
5. Секреты, содержимое логов и границы использования данных.
6. Метрики и наблюдаемость.
7. Содержание тестов и проверяемые сценарии.
8. Понятность кода и сложность зависимостей.
9. Соответствие существующему API и правилам проекта.

Отличие API или выбор настоящего LLM в ответе A сами по себе не являются ошибкой: исходный короткий запрос не задавал наш API и не сообщал об эмуляции. В этом критерии оценивается объём адаптации к существующему проекту, а не способность угадать скрытые требования.

## Результаты сравнения

Ответ B лучше соответствует существующему проекту по API, именам классов, разделению слоёв, настройкам и наблюдаемости. При этом ответ A уже содержит полезные инженерные решения. Эксперимент не подтвердил предположение «без контекста AI обязательно пишет плохой контроллер с прямым вызовом модели».

| Критерий | A — только задача | B — задача и контекст |
| --- | --- | --- |
| Слои | Отдельные Controller, Service и HTTP-адаптер за `LlmGateway`; все типы в одном пакете | Нужные пакеты и цепочка Controller → Service → ClassificationClient → AiGateway → LlmClient |
| Заменяемость | Есть интерфейс `LlmGateway`, но показана одна реализация для реального API | Есть `LlmClient`, две локальные реализации, выбор основного и резерва по конфигурации |
| API и категории | `/api/classifications`, русские значения категорий, `Optional.empty()` превращается в 422 | `/api/appeals/classify`, коды `CREDITS/CARDS/TRANSFERS/OTHER`, нужные DTO и `ApiError` |
| Валидация | `@NotBlank`, максимум 4000; строгая проверка JSON, полученного от внешней модели | Максимум 2000 до `strip()`, запрет чисел и boolean вместо текста; проверка `null` и категории в ответе провайдера |
| Ошибки и устойчивость | Таймаут соединения 2 секунды и чтения 15 секунд; повторы сознательно исключены; второго провайдера нет | Таймаут попытки, ограниченные повторы, один резерв, ограниченная очередь, отмена и разделение типов сбоев |
| Безопасность | Ключ через окружение, разделение system/user, безопасные публичные ошибки; оговорена политика передачи данных во внешний сервис | Сеть и ключи не нужны, инструкция отделена от текста, в логах только технические поля |
| Метрики | Мониторинг предложен как дальнейшая работа; реализации метрик нет | Показаны `llm.calls`, `llm.call.duration`, `llm.fallbacks` с ограниченными тегами |
| Тесты | Листинги для Service, HTTP API и адаптера через `MockRestServiceServer` | Листинги для Service, HTTP API и Gateway, тест отмены через latch; остальные сценарии перечислены отдельной матрицей |
| Простота | Меньше механизмов, один внешний адаптер; для запуска нужны ключ и модель | Соответствует четырём согласованным зависимостям, но добавляет три дополнительных вида исключений и больше кода |
| Предметные правила | Для перевода с упоминанием карты предлагает приоритет `TRANSFERS` | Для нескольких распознанных тем возвращает `OTHER`, как задано контекстом |

### Примеры влияния контекста

**Контракт API.** В A явно предложено `POST /api/classifications` и `{"category":"переводы"}`. В B показано `POST /api/appeals/classify` и `{"category":"CREDITS"}`. Второй ответ можно обсуждать в терминах уже существующих DTO и маршрута. Первый потребовал бы изменения предложенного кода либо нашего публичного API; в текущем проекте сохраняем согласованный контракт.

**Недостаточные данные.** A использует `Optional<Category>`, внутренний `UNKNOWN` и HTTP 422. B использует доменный `OTHER` и успешный ответ. Оба подхода отделяют неопределённость от сбоя провайдера, но по-разному выражают её во внешнем контракте. Первый запрос не сообщал, какой вариант нужен, поэтому выбор 422 не считается сам по себе архитектурной ошибкой.

**Границы компонентов.** В A `ClassificationService` зависит от интерфейса `LlmGateway`; HTTP-запрос к модели расположен в `OpenAiLlmGateway`, а не в Controller. Это полезная абстракция. B дополнительно воспроизводит наш `ClassificationClient`, внутренние модели `LlmRequest/LlmResponse` и `AiGateway`, который маршрутизирует обращения. Контекст уточнил конкретные границы проекта, а не впервые сообщил модели о существовании слоёв.

**Устойчивость.** A задаёт `.connectTimeout(Duration.ofSeconds(2))` и `factory.setReadTimeout(Duration.ofSeconds(15))`. Отсутствие повторов там объяснено стоимостью и задержкой. B реализует именно нашу политику: `max-attempts` для основного провайдера, резерв один раз, два потока и очередь на десять задач. Разница связана с явно переданными требованиями; наличие слова «timeout» в обоих ответах не означает одинаковую реализацию.

**Данные и безопасность.** В A ключ указан как `${LLM_API_KEY}`, а не записан непосредственно в YAML. Сообщение пользователя передаётся отдельной ролью. В B секреты вообще не нужны, потому что контекст требует локальную эмуляцию. Неверно приписывать A утечку ключа или утверждать, что B доказал безопасность реальной LLM: внешняя модель в B не вызывается.

**Проверки.** A показывает тест обработки `SocketTimeoutException` у HTTP-адаптера: это проверка реакции на такую ошибку, а не измерение реального времени ожидания. B показывает ожидание с `CountDownLatch` и проверку прерывания медленной задачи. При этом B сам указывает, что часть тестов только перечислена в матрице. Ни один набор не запускался в этом эксперименте.

### Что осталось проверить и уточнить в B

1. **Не передан полный словарь.** В промпте B есть ссылка на README, но само содержимое README и исходников запрещено читать. В предложенном `OpenAiLlmClient` нет слова «ипотека», хотя базовый проект его распознаёт. По приведённому алгоритму текст «Нужна ипотека» даст `OTHER`; это статический вывод из словаря, не результат запуска. Недостающий словарь нельзя требовать угадать. В следующий содержательный запрос стоит передать нужные наборы слов или приёмочные примеры, а не одну ссылку на файл.
2. **Прерывание при завершении задачи.** В B флаг проверяется перед попыткой и обрабатывается `InterruptedException`, но после успешного `future.get(...)` проверки флага нет. При совпадении завершения задачи с прерыванием это требует отдельной проверки. Базовый проект уже содержит такую защиту и тест `interruptionIsNotLostWhenProviderCompletesAtTheSameTime`. Из ответа B нельзя заключить, что этот пограничный случай закрыт.
3. **Статус при прерывании.** B предлагает отдельный `LlmInterruptedException` и прямо пишет, что обработчик вернёт 500. В базовом проекте используется `ClassificationUnavailableException` и 503. Промпт задавал остановку обработки и восстановление флага, но не определял этот HTTP-статус явно. Это ещё один пример требования, которое нужно передавать вместе с контрактом, если важна точная совместимость.
4. **Дополнительные типы и перенос кода.** B добавляет `LlmTimeoutException`, `LlmRejectedException`, `LlmInterruptedException`, тогда как текущая реализация использует стандартные исключения Java там, где их достаточно. Дополнительные типы не обязательно неверны, но их польза для нашего небольшого проекта не обоснована. Кроме того, автор B явно опускает импорты и часть тестовых листингов; ответ не является готовым патчем к репозиторию.

Эти наблюдения не внесены обратно в исходный ответ B. Они показывают, зачем после генерации нужны инженерная проверка и проверяемые примеры. Возможные дефекты листингов здесь не выдаются за подтверждённые падения тестов.

## Принятые и отклонённые предложения

Сохраняем в проекте принципы, которые подтверждаются обоими ответами: отделение HTTP от обработки обращения и провайдера, общий контракт, валидация, безопасные ошибки, разделение инструкции и клиентского текста, тесты без реальной модели. Из B полезны соответствие нашей цепочке слоёв, явная политика повтора и резерва, ограниченный исполнитель, технические метрики и тестирование количества вызовов. Эти решения уже присутствуют в базовой реализации; совпадение с ответом не означает, что они были внедрены заново.

Для текущей работы отклонены изменения маршрута, русские значения в поле `category`, лимит 4000, Java 17 вместо 21, замена `OTHER` на 422 и обязательный внешний API из A. Это несовместимость с согласованными требованиями, а не утверждение, что каждое такое решение непригодно вообще.

Из B не переносим целиком новый набор исключений и переписанные классы. Сохраняем действующий словарь, обработку прерывания и существующие тесты. Идеи A о строгом разборе JSON внешней модели полезны при будущем настоящем HTTP-адаптере, но к типизированному ответу текущих эмуляций не применяются напрямую. Предложения о дополнительных мерах для банковского production не расширяют объём этой лабораторной.

## Вывод по эксперименту

Короткого задания оказалось достаточно для содержательного ответа со слоями, абстракцией, безопасным хранением ключа и тестами. Но недостающие проектные и предметные требования AI выбрал самостоятельно: другой API, другой способ отказа от классификации, другие версии и настоящий внешний провайдер.

После добавления контекста ответ стал существенно ближе к нашему проекту: сохранил API, категории, пакеты, эмуляции и правила Gateway. При этом из неполного контекста не восстановился весь словарь, а отдельные детали обработки прерывания разошлись с базовой реализацией. Для следующего запроса полезнее добавить конкретные примеры вроде «Нужна ипотека → CREDITS» и нужные пограничные тесты, чем просто увеличить объём общих инструкций.

Практическое значение context engineering в этой работе — передать актуальные факты, контракты и критерии проверки именно для выполняемой задачи. Полученный ответ всё равно требует чтения кода и проверок; соответствие документации не заменяет их. Это вывод из данного парного примера, не универсальная оценка всех ответов модели.

## Границы выводов

Это один парный пример, а не статистическое исследование. В B одновременно добавлены сведения и явные ограничения; длина промпта тоже отличается. Эксперимент не позволяет отделить вклад каждого фактора и не доказывает общее превосходство подхода на любых задачах. Отдельные агенты остаются внутри общего инструмента с его служебными инструкциями. Повторный запуск может дать другие формулировки и решения.

Сравнение основано на чтении ответов. Сборка и исполнение предложенного ими кода в этот этап не входят. Рабочий проект не заменяется сгенерированными листингами. Результаты предыдущих 111 тестов относятся к базовой реализации проекта, а не к этим ответам AI.
